Modern Architecture for Quantum Computers

An oracle-based memory sector, a small set of active qubits, and a clock that packs operations into ticks. Together they let a classical controller absorb whole classes of quantum gates and share one oracle across parallel algorithm instances.

Author Nischal Keshav Edition Whitepaper v1.0 · September 2026 Basis Working paper, 7 pp.
Summary

Quantum computing research has concentrated on algorithms and, more recently, on qubit hardware. Far less attention has gone to the layer between them: how memory is organised, how operations are scheduled, and how the machine keeps its qubits coherent for the duration of a program. This paper proposes an architecture for that layer.

The design has two components. The first is an oracle-based memory unit: a sector of inactive, read-only qubit lines that answers address queries, kept physically separate from a small set of active lines where computation happens. A classical controller sits between them. The second is a quantum clock cycle: operation tools fire on every tick, and the design packs as many operations into a tick as possible so that a program finishes in fewer cycles and accumulates less error before measurement.

01The architecture gap

The applications of quantum computers have been analysed exhaustively, from materials science to breaking public-key encryption. Work on physical qubits has grown quickly. What has been passed over is the architecture: a definitive account of how memory and logic are managed once a program is more than a circuit on a whiteboard.

A hand-wave at memory works when the goal is to show that some task is possible in principle. It does not work when the goal is a productive machine. The classical computer became useful only after the von Neumann layout gave engineers a fixed vocabulary of memory, control and arithmetic. This paper attempts the same for a quantum machine. It is not a physical project, but it references the physical processes, in particular decoherence, that constrain every choice.

02Design objectives

Two requirements govern the design. Both are stated in the language of asymptotic complexity so that they can be checked as qubit counts grow.

Scalable

Efficiency must hold as the number of qubits and the number of operations increase. Resource cost is measured in O-notation: operations and memory slots needed as input size grows.

Compatible

Every function that existing theoretical models can compute must run on this architecture at the same asymptotic efficiency. Nothing that is possible on a gate-model machine may become impossible here.

03The oracle-based memory unit

The memory centre of the machine behaves as an oracle. When it receives a string of bits (an address), it returns some other qubits. The paper uses line as a synonym for qubit, because the language of wiring reads more naturally when describing a machine.

Lines are of two kinds. Inactive lines make up the memory sector. They are read-only from the program's point of view and hold the function or data the program consults. Active lines are where the majority of computation happens. Each active line has an operation tool attached that can apply a unitary to it on a clock tick. Inactive lines also have tools attached, but those tools never commit a change.

Separating the two kinds of line pays off in two ways.

  1. Fewer physical resources and fewer phase-flip errors. Qubits that are about to be operated on have to be prepared differently from qubits that are only being stored. If the two are not differentiated, the qubits that are not the target of an operation have a much higher chance of suffering a phase-flip error during it (De Wolf, 2023). Keeping the memory sector inert protects it.
  2. Some quantum operations become classical adjustments. Because the controller owns the mapping from address to line, several operations that would normally require a quantum gate can be performed by editing the address table. Pauli-X and SWAP are the paper's examples. Section 04 develops this.

A caution follows from the physics. Operations must preserve superposition, and simply "flipping a switch" on a line would force it to decide a state. Quantum operations are unitary, reversible and represented by matrices. Whatever technology applies them, it must do so either instantaneously or in a way that never requires the qubit to choose between states mid-operation. The architecture is agnostic about which technology is used, so long as it is viable under the current model of quantum computing.

04Gates that become address changes

The claim in section 03 is that some gates can be removed from the quantum circuit entirely. The argument runs as follows.

Every quantum gate is a unitary matrix. Let U be any transformation the machine is about to apply to its active lines, and let Xn be a Pauli-X gate acting on the nth line (the identity on every other line). The product of two unitaries is unitary:

(U Xn)†(U Xn) = Xn† U† U Xn = Xn† Xn = I

So U Xn is itself a single valid transformation, and the X gate need not be applied as a separate step. The same holds for a SWAP between lines i and j, which is a permutation matrix Pij: U Pij is unitary. In this architecture the controller does not even need to compile a new operator. Because it owns the address table, a SWAP is performed by exchanging the two address entries, and an X is recorded as a flip flag on the line's entry that the next lookup honours. No quantum gate fires, so no clock tick is spent and no gate error is introduced.

Scope of the proofThe proof shows the combined transformation exists and is legal. It does not say that a dedicated U Xn operator must be built for each case; other technology can realise it. The paper's LaTeX derivation was left for its final version. The derivation above restates the argument in full.

05The quantum clock cycle and error

With memory in place, the paper turns to how operations are timed and how error is handled. The device is a clock. On every tick, the operation tools attached to the active lines fire. The scheduling rule is simple: apply as many operations as possible in each tick. Fewer ticks means less wall-clock time in superposition, and therefore less exposure to the error-applying operator the paper models as a Kraus operator.

Calibration and similar mechanical techniques remove some error, as in any machine, but some error is unavoidable. The standard remedy is repetition: run the function several times and take the consensus. Repetition requires a machine that already mostly works and consumes a great deal of resource. Section 06 shows how the memory architecture makes repetition cheap.

06Sharing the oracle: parallel Grover

Grover's algorithm takes a function, presented as an oracle, and a goal value, and searches for the input that produces the goal. It is a workhorse in materials science and other fields where a black-box function must be inverted (IBM, n.d.). It is also the natural test of this architecture, because the architecture's memory sector already is an oracle. The values of the function are loaded into the inactive lines as a list, and Grover's oracle query becomes a memory lookup.

Running Grover once shows nothing special. Running it several times at once does. Repetition is the standard error remedy, and on a conventional machine three simultaneous instances against a 128-line oracle need three copies of the oracle, so three times the qubits. Here the three instances share the one oracle. Only the active lines are duplicated, and the active register for a search over N entries is about log2 N lines.

The gap widens with the number of instances, since the oracle is paid for once regardless. The paper's own example is three instances; the chart below extends the same accounting to eight.

The paper's hypothetical benchmark concluded that the architecture has the potential to assist any algorithm that consults a black-box function, since every such algorithm can treat the memory sector as its oracle and share it across repetitions. It also frames this as linear optimisation obtained without new technology: the same qubits, arranged differently.

07Assumptions and open work

The source is a working paper, and the whitepaper preserves its scope. The following points are stated so that a reader can weigh the claims.

  • Hand-calculated benchmark. The Grover qubit counts in the paper were computed by hand. Figures 6 and 7 rebuild them from an explicit formula, and the formula is given in each caption so it can be checked.
  • Error model is qualitative. The paper names a hypothetical Kraus operator as the source of error but gives no rates. Figure 5 uses an assumed 1% per tick purely to illustrate the direction of the effect.
  • Physical realisation is out of scope. The architecture is stated to be compatible with any operation technology that keeps superposition intact. Which technology, and how the memory sector's oracle lookup is physically implemented, is not addressed.
  • Grover's per-qubit saving is unquantified. The paper reports it as linear with an algorithm-dependent constant.
  • Formal derivations pending. The paper marks its LaTeX proof for a later version. Section 04 restates the unitary-product argument in full; a longer treatment covering compatibility (objective 2) for arbitrary circuits remains to be written.
